## 21. 评审与修订记录

> 本记录保留 2026-10-28 评审当时的上下文与章节编号；当前本地实现已升级到 Astro 7.4，章节也拆分为多个文档，见 [技术选型](../02-架构设计/02-技术选型.md) 与 [本地开发与部署](../04-运维部署/01-本地开发与部署.md)。

以下为 2026-10-28 评审核对后直接修改的内容，按影响程度排序。原方案的主体架构保留，问题集中在免费额度、缓存、认证和边界条件。

| # | 原设计问题 | 本次修订 |
|-|-|-|
| 1 | 未计入 Workers 免费版 10 ms CPU 限制，却假设全站 SSR 可稳定运行 | 第 13、17、18 章补充 CPU 约束、阶段零压测和 Go/No-Go；第 20 章改为“先验证再开发” |
| 2 | 在 workers.dev 上设计“发布后主动清理页面/列表缓存”，但该环境没有 zone 级 Purge | 第 10 章改为第一版不做整页边缘缓存；图片内容哈希 + 浏览器缓存；后续优先评估 Workers Cache，版本化 key 兜底 |
| 3 | Access 与 Astro Static Assets 组合下，`ctx.access` 不会传给用户 Worker | 第 9.1 章补充 JWT 校验/内部 HMAC 两种方案，并处理 Access 登录过期时的 302/HTML |
| 4 | R2 key 固定为 `.webp`，但方案不做图片转码，JPEG/PNG 会被错误命名 | 第 6.5、8.2 章改为 `<hash>.<ext>`，扩展名按文件头识别 |
| 5 | SEO 承诺 slug 修改配置 301，但 redirects 表被列为“可选后续” | 第 12 章改为第一版 slug 发布后不可修改；先实现 redirects 再开放修改 |
| 6 | `post_tags` 只有 `(post_id, tag_id)` 主键，按标签查文章会全表扫描 | 第 6.4 章补充 `(tag_id, post_id)` 索引 |
| 7 | `assets` 缺少内容哈希，无法去重，也无法可靠复用 R2 对象 | 第 6.5 章补充 `content_hash` 唯一约束、先查重复用、失败清理和延迟删除 |
| 8 | 未提 D1 单条 SQL 100 KB、单次 50 条查询、单行 2 MB 限制 | 第 6.2、13 章补充正文 80 KB 上限、batch 和查询数量约束 |
| 9 | 未提 Markdown 原始 HTML 导致的存储型 XSS | 第 9.2 章补充禁用原始 HTML、过滤危险链接、发布时净化和 CSP |
| 10 | 阶段二计划加搜索，但未说明 FTS5 会让 `wrangler d1 export` 失败 | 第 16 章补充备份前删除 FTS 虚拟表或只导出业务表，恢复后重建索引 |
| 11 | 测试方案只写“后端/前端测试”，没有 Rust Wasm 的可执行测试路径 | 第 15 章补充 Miniflare 端到端、cargo test 只测纯逻辑、文章页 CPU 压测 |
| 12 | Astro 6 的 Cloudflare adapter 默认 `imageService: 'cloudflare-binding'`，可能意外调用 Cloudflare Images | 第 4.1 章固定 `passthrough`，不使用 Astro `<Image>` 处理 R2 图片 |
| 13 | 后台预览与公开页可能使用不同 Markdown 渲染器，效果不一致 | 第 4.2、11.2 章统一为服务端同一渲染器，并增加草稿自动保存 |
| 14 | “0 元/年、单厂商、全球访问”的边界未量化，忽略 R2/Zero Trust 可能要求支付方式及大陆访问稳定性 | 第 1、13、18、20 章补充账单提醒、无 SLA、大陆访问风险和 Plan B |
| 15 | `packages/contracts` 仅写“字段说明”，前后端类型会漂移 | 第 5 章补充 ts-rs/OpenAPI 代码生成建议 |

补充（同日）：核对 2026-10 文档后确认，`workers.dev` 不应依赖传统 Cache API；Cloudflare 已提供 zoneless 的 Workers Cache（任意计划可用、支持 `Cache-Tag` purge，但缓存命中仍计请求，启用后静态资源也计费）。第 10、17、20 章已将其列为 CPU 不达标时的优先验证项，而非第一版前提。
